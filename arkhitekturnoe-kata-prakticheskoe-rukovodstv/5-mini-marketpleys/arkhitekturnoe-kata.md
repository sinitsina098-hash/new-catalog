### 4\. 📝 Представьте решение (20 минут)

**Краткое описание архитектуры:**

Система спроектирована на базе микросервисной архитектуры с единой точкой входа через API Gateway и балансировщиком нагрузки. Такой подход позволяет гибко масштабировать отдельные сервисы и упрощает поддержку.

Хранение данных разделено:

-  бизнес-информация (пользователи, заказы, платежи) размещается во внутренней реляционной базе;

-  медиафайлы (фото товаров) хранятся в объектном облачном хранилище с CDN для быстрой доставки.

Ключевые сервисы:

-  **Auth Service** - регистрация, авторизация, управление ролями;

-  **Catalog Service** - управление товарами, поиск и фильтрация;

-  **Order Service** - корзина и процесс оформления заказов;

-  **Payment Service** - интеграция с внешним платежным шлюзом, соответствующим PCI DSS;

-  **Messaging Service** - чаты между продавцами и покупателями с уведомлениями;

-  **Review Service** - отзывы и рейтинги продавцов;

-  **Fraud Detection Service** - автоматическая и ручная модерация объявлений;

-  **Notification Service** - push, email и SMS-уведомления.

Особое внимание уделено безопасности: используются TLS для шифрования, защищённое хранение персональных данных и интеграция с сертифицированным платёжным провайдером.

Архитектура поддерживает мультиплатформенность (iOS, Android, Web), что расширяет охват аудитории, а использование облачных сервисов снижает нагрузку на команду и расходы на инфраструктуру.

**Защитите решение перед группой:**

### Демонстрационный кейс работы маркетплейса №1

**Ситуация:**\
Иван - продавец, который выставляет на продажу смартфон.\
Анна - покупатель, которая ищет смартфон в приложении.\
Модератор Ольга - администратор платформы.

**1\. Размещение товара (Иван):**

-  Заходит в приложение -> проходит авторизацию через **Auth Service**.

-  Создаёт объявление через **Catalog Service**: фото загружаются в облачное хранилище S3 + CDN.

-  Объявление автоматически проходит через **Fraud Detection Service** (проверка описания и фото).

-  Если всё ок, товар попадает в каталог. При подозрении - уходит на ручную проверку модератору.

**2\. Поиск и фильтрация (Анна):**

-  Через **Catalog Service** Анна находит смартфон, используя фильтры (по цене и бренду).

-  В карточке товара видит фото (подгружено из CDN), рейтинг продавца (**Review Service**) и кнопку "Написать продавцу".

**3\. Общение и уточнение деталей:**

-  Анна пишет Ивану в чат через **Messaging Service**.

-  Иван сразу получает push-уведомление от **Notification Service**.

-  Чат хранится в кэше и очередях, что обеспечивает мгновенную доставку сообщений.

**4\. Оформление заказа и оплата:**

-  Анна добавляет товар в корзину (**Order Service**) и подтверждает покупку.

-  Оплата проходит через **Payment Service** -> транзакция отправляется во внешний PCI DSS-сертифицированный шлюз.

-  После успешной оплаты Иван получает уведомление о заказе.

**5\. Доставка и завершение сделки:**

-  После доставки Анна оставляет отзыв и ставит рейтинг Ивану через **Review Service**.

-  Рейтинг автоматически влияет на доверие к продавцу и его видимость в поиске.

**6\. Работа модератора (Ольга):**

-  Следит за подозрительными объявлениями в **Fraud Detection Service**.

-  Может вручную отклонить товар или заблокировать продавца.

-  Получает аналитические отчёты о количестве жалоб и подозрительных объявлений.

### Что показывает этот кейс:

-  **Безопасность:** мошеннические объявления отсекаются на старте.

-  **Удобство:** покупатель быстро находит товар, получает мгновенные уведомления.

-  **Надёжность:** сообщения, заказы и платежи проходят через отдельные сервисы, что исключает зависания.

-  **Масштабируемость:** каталог и чат могут расти независимо, нагрузка распределяется через API Gateway и очереди.

-  **Бизнес-ценность:** довольные покупатели -> доверие к платформе -> рост числа сделок.

### Демонстрационный кейс №2 - нестандартная ситуация

**Ситуация:**\
Пользователь Сергей пытается разместить объявление о продаже «нового iPhone» по цене в 10 раз ниже рынка.\
Мария - покупатель, которая видит это объявление и хочет его купить.\
Модератор Алексей следит за системой.

**1\. Размещение подозрительного объявления (Сергей):**

-  Сергей авторизуется через **Auth Service**.

-  Загружает фото и описание товара в **Catalog Service**.

-  Фото и описание уходят в **Fraud Detection Service**.

**2\. Срабатывание антифрода:**

-  Алгоритмы замечают подозрительное расхождение: описание товара -> «iPhone 17 Pro», цена -> слишком низкая.

-  Сервис отмечает объявление как **«подозрительное»** и передаёт его на ручную проверку.

**3\. Работа модератора (Алексей):**

-  Модератор получает уведомление от **Fraud Detection Service**.

-  Проверяет детали: видит признаки мошенничества (несоответствие фото и описания, цена сильно занижена).

-  Через интерфейс модератора блокирует объявление.

**4\. Действия покупателя (Мария):**

-  Мария пытается найти смартфон через **Catalog Service**.

-  Заблокированное объявление не попадает в поисковую выдачу.

-  Вместо него Мария видит только проверенные предложения.

**5\. Дополнительные меры:**

-  Система фиксирует Сергея в «группе риска» в **Auth Service**.

-  При повторных попытках мошенничества его аккаунт может быть автоматически заблокирован.

-  Администратор получает отчёт о подозрительных действиях для дальнейшего анализа.

### Что показывает этот кейс:

-  **Антифрод работает на входе:** подозрительные товары не доходят до покупателей.

-  **Гибридная модерация:** автоматическая проверка + ручное подтверждение повышают точность.

-  **Покупатель защищён:** Мария видит только безопасные объявления и не теряет деньги.

-  **Продавец-мошенник изолирован:** попытки обхода системы фиксируются.

-  **Репутация платформы сохраняется:** минимизация числа жалоб и юридических рисков.
